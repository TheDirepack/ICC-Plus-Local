# Structure, layout, and player flow

The player should not have to read the CYOA twice to learn how the first choice worked.

## Common player expectations

These are useful defaults, not rules every project must follow.

- The premise and basic rules appear before the first choice that depends on them.
- Costs, gains, pick limits, and prerequisites are visible near the affected choice.
- Selecting something produces a clear visual state.
- Point totals stay easy to find while spending.
- A later section does not quietly invalidate an earlier build without warning.
- Long projects offer a practical way to review or save the build.
- The page remains usable on a phone.
- A finished build has a clear stopping condition.

Break an expectation when the project gets something specific from breaking it. If a rule surprise is part of the fiction, make sure it creates an intended experience rather than an accidental gotcha.

## Opening and goal text

The opening should tell the player what they are making or deciding, the important limits, and what the first meaningful decision is. Avoid generic welcome text that delays the actual premise.

The ending or goal text should tell the player what a finished legal build means and what the build is meant to accomplish or represent. If a scenario judges the build, state enough of that standard before spending begins.

A start and an end are useful only when they orient decisions. Decorative introduction and conclusion text should not replace the player contract or completion rule.

## Common section structures

### Linear build

The player moves from top to bottom through a mostly fixed sequence.

This works well when later sections depend on earlier context. It is the easiest structure to understand.

### Reference-first build

The project explains the setting, rules, or threat, then begins choices.

Use this when the player cannot judge options without context. Keep the required reading short enough that the player reaches an actual decision quickly.

### Hub-like build

The player can choose categories in almost any order.

This fits independent point-buy categories or large builders. The point system and section labels must make cross-category spending easy to track.

### Progressive reveal

Earlier choices reveal later content.

This keeps the page focused but can conceal options. Use it when hidden content is irrelevant until unlocked, not merely to make the page look shorter.

### Branching path

A major choice sends the player into one of several different content paths.

Make the branch point clear. If players may want to compare paths before committing, do not hide all downstream information too early.

## Common card layouts

### Image above text

This is the standard card pattern for choices with short to medium descriptions. It works well when images share a consistent aspect ratio.

On phones, very tall portrait images can push the description far below the choice title. Crop or use a side layout when that becomes annoying.

### Image beside text

Use this for longer descriptions or portrait art. It can reduce vertical scrolling on wide screens.

Test the narrow layout. Side-by-side cards often need to stack on phones.

### Text-first or text-only

Use it when the decision is conceptual and art would add little. Break long prose into readable blocks. A wall of similar text cards can become hard to scan.

### Compact catalog

Many short choices appear in a dense grid.

Use it for perks, items, traits, tags, or other short entries. Keep names distinctive and descriptions brief. Do not use a high column count for paragraph-heavy cards.

### Large feature cards

A few large cards use prominent art and more text.

Use this for major paths, worlds, factions, companions, or scenarios where each option deserves space.

## Keep related choices close

If one choice unlocks, upgrades, replaces, or strongly modifies another choice, keep them near each other when the format allows it. If they must be separated, name the connection on both ends.

A player should not have to remember a prerequisite from several screens earlier just to understand why a later option exists.

## Hidden content and discoverability

Hiding irrelevant content can reduce clutter. Hiding desirable content with no hint can make it effectively nonexistent for many players.

For an unlock that matters, give the player at least one of these:

- a visible locked card,
- a short hint about the unlock condition,
- a nearby note that more options can appear,
- a summary that records undiscovered branches when discovery is part of the game.

Fully secret content works best when missing it is acceptable. Do not make core balance, required progression, or the only satisfying ending depend on an invisible condition unless the surprise is the point of the design.

## Branching without uncontrolled growth

Narrative branches do not need to remain separate forever. A useful structure is to let a scene branch locally and then merge at a natural checkpoint. Earlier choices can still matter through changed text, requirements, scores, later options, or ending conditions.

This keeps the project writable without turning earlier choices into decoration. For longer narrative CYOAs, plan where branches merge and where earlier decisions pay off later.

Use full permanent divergence for decisions that justify the extra content, especially major routes or endings. Do not create a separate permanent branch for every small choice.

## Section order

Section order should follow information dependencies.

A useful default for a character or scenario builder is:

1. Premise and rules.
2. High-level identity or scenario context.
3. Budget-setting choices.
4. Core build choices.
5. Supporting options.
6. Drawbacks, if they are best judged after seeing benefits.
7. Companions, equipment, missions, or other premise-specific sections.
8. Final scenario, goal, or ending where applicable.
9. Build summary and save or export tools.

This is only a starting pattern. Move a section earlier when later choices depend on it.

## Drawback placement

There is no universal correct position.

Place drawbacks early when they define the player's available budget or strongly change how later choices should be judged.

Place them later when their cost only makes sense after the player has seen what they are giving up or buying.

For long interactive projects, another option is to allow temporary overspending and let the player resolve the budget when they reach drawbacks. If you do this, make the negative balance obvious.

## Scenario placement

If the project asks the player to prepare for a scenario, give enough scenario information before the relevant purchases.

Do not reveal the standard by which a build is judged only after the player has spent all resources unless surprise is the intended game.

## Navigation and backtracking

Backtracking is most annoying when it is required by hidden information.

Reduce it by:

- placing budget-changing rules before major spending when practical,
- revealing prerequisites near the choices they affect,
- keeping important point totals visible,
- using clear section titles,
- avoiding long dependency chains across distant Rows,
- using build summaries for long projects.

## Choice density

Card width should follow content length.

- One or two large cards per row suits long descriptions or major path choices.
- Three or four often suits medium cards on desktop.
- Higher counts suit short catalog entries.

Do not choose the column count first and then force the writing to fit it.

## Mobile expectations

Treat phone use as a normal case.

Check:

- Body text size.
- Tap targets.
- Point bar scrolling.
- Multi-select sliders and counters.
- Images that become too tall.
- Side-by-side layouts that need to stack.
- Large dialogs and menus.
- Backpack use.
- Build save and import controls.

ICC Plus 2 includes responsive Choices Per Row controls. Use them before custom CSS when they solve the problem.

## Long CYOAs

Long projects need stronger navigation and memory aids than short projects.

Useful tools include clear section names, visible budgets, progressive reveal, a Backpack, build save, Choice Import, search where supported, and concise reminder text near later dependencies.

Do not make the player remember a rule from 100 choices earlier if the interface can show it again where needed.
