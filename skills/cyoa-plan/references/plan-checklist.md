# Plan checklist

## Premise and player contract

- [ ] The premise fits in one clear sentence.
- [ ] Non-goals are recorded so unrelated ideas do not expand the project by accident.
- [ ] The plan states what the player is making or deciding.
- [ ] The plan states the main limits.
- [ ] The plan states what a finished build contains.

## Format and rules

- [ ] Main format is named.
- [ ] Every currency or pick limit has a reason.
- [ ] Drawbacks have a defined role if used.
- [ ] Repeated purchase, prerequisites, discounts, and exclusions are recorded if used.
- [ ] Completion rule is explicit.

## Structure and coverage

- [ ] The complete section skeleton exists before bulk prose.
- [ ] Every section has a player-facing purpose.
- [ ] Section dependencies are recorded.
- [ ] Related choices, upgrades, and prerequisite information are placed near each other where practical.
- [ ] Important hidden or locked content has a discoverability plan.
- [ ] Important choices have distinct roles or reasons to exist.
- [ ] Important choices have a useful basis for decision and an intended consequence or payoff.
- [ ] Section order minimizes avoidable backtracking.
- [ ] Layout assumptions match expected text length.
- [ ] Phone layout is considered.

## State and implementation

- [ ] Point Types are listed.
- [ ] Variables are limited to state that needs them.
- [ ] Groups and Global Requirements are listed where useful.
- [ ] ID policy is defined.
- [ ] Save, Choice Import, and Backpack needs are decided separately.

## Calibration, balance, and tests

- [ ] A representative sample sets title, prose, rules, cost, and image conventions before bulk authoring.
- [ ] At least three full sample builds exist for a medium project.
- [ ] A large point-buy project uses a broader build sweep, commonly a dozen or more varied builds when practical.
- [ ] Specialist and generalist cases were compared where relevant.
- [ ] Drawback-heavy or exploit-seeking cases were tested where relevant.
- [ ] Major gates have passing and failing cases.
- [ ] Requirement paths were checked for reachability and cycles where relevant.
- [ ] Boundary and state-loss cases exist for complex rules.
- [ ] Repeated content families have a deliberate source-side baseline/delta plan when inheritance would reduce duplication.
- [ ] Source-side templates or inheritance will compile to explicit player-facing content without leaking authoring metadata.
